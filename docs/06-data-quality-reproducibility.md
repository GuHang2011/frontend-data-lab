# 06 · 数据质量与可复现性

一个可信的演示应能回答：数据从哪里来、哪些记录被接受、指标如何计算、别人如何复现，以及哪些结论尚未验证。

## 四层质量检查

1. **结构：** 表头和列数是否符合契约。
2. **字段：** 日期能否解析、金额是否整数、枚举是否已知。
3. **关系：** 订单 ID 是否唯一、状态计数之和是否等于全部订单数。
4. **语义：** 退款占比采用什么分母、金额按什么日期归属。

前三类可以部分自动化，第四类需要业务或研究定义。通过类型检查不能证明指标具有所需含义。

## 为什么导入采用事务

假设前 500 行合法，第 501 行金额非法。如果每批立即提交，数据库会留下半份新数据；页面可能显示一个没有明确来源的残缺结果。本例只将分块作为内存缓冲边界，全部导入共享一个事务。失败时回滚，旧数据保留。

一次大事务可能持有较长锁并增加日志空间，因此真实大规模导入更常用 staging table、批次 ID、质量门槛与原子切换。不能把“分块写入”直接等同于“生产级 ETL”。

## 可复现不是只有 seed

固定种子让同一生成器在同一环境下重复产生相同输入。还应记录代码版本、Python 版本、参数和输出校验值；随机数库或生成算法变化可能改变结果。当前快照包含种子和生成器标识，没有把当前时间写入数据，因此默认重建不会因为时间戳产生无关差异。

```bash
python --version
python -m src.pipeline --rows 12000 --seed 42 --chunk-size 500
python -m unittest discover -s tests -p "test_*.py" -v
node --test tests/dashboard.test.cjs
```

分块一致性测试比较 chunk size 为 1、7、500 的聚合结果；这是在验证“实现细节不改变业务结果”。非法行与重复 ID 测试则验证失败后的数据库仍保持旧值，不只是检查函数抛出了异常。

## 教学结果与研究证据的边界

合成订单的区域、渠道和状态按预设概率生成。观察到的退款率、收入曲线与区域差异不能外推到真实人群或市场。数据没有现实采样框、未观测混杂因素，也没有可靠的因果识别设计。

若要把本项目扩展为研究，应先明确研究问题、合法数据来源、训练/验证/测试划分、基线、评估指标、重复实验和不确定性。随机拆分时间序列可能造成未来信息泄漏；先用全量数据拟合标准化参数同样会泄漏。

当前仓库没有模型训练结果、论文实验、集群基准或“提升百分比”。需要记录的是实际运行日志与可检查结果，而不是为作品集补上未经测量的成绩。
